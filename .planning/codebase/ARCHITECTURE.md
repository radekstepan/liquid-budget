# Architecture — YNAB4 Alternative SPA

## 1. Overview
- **What it is:** YNAB4-compatible envelope-budgeting personal finance app (YNAB4 data model: budget months, category groups/categories, payees, accounts, transactions with splits/transfers, monthly assignments, reconciliations, recurring templates).
- **Monorepo:** Yarn 4 workspaces (`apps/*`, `packages/*`), orchestrated by Turborepo (`turbo.json`: `dev`, `build`, `lint`, `typecheck`, `test`, `coverage`).
- **Runtime:** Next.js 16 (App Router) + React 19 SPA in `apps/web`; SQLite (better-sqlite3 via Drizzle ORM) persisted in `budget.db` (+ `budget.test.db`); Tailwind CSS 4.
- **Style:** Server owns persistence/migrations/queries; `logic` owns pure domain rules; `ui` owns all views; `web` is thin glue (routes + API handlers + shell).

## 3. Entry Points & Routing
- **Web entry:** `apps/web/src/app/layout.tsx` → `components/BudgetAppShell.tsx` → `@ynab/ui` `BudgetApp`. Client-side view routing via catch-all `app/(app)/[[...slug]]/page.tsx` — the slug selects only `budget` / `reports` / `transactions` (`AppView` in `logic/page-title.ts`, with optional month/account segments); other views (Payees, Snapshots, Themes, Settings, …) are in-app state, with `navVisibility.ts` controlling sidebar.
- **API surface** (`apps/web/src/app/api/*/route.ts`, validated by `schemas.ts` + zod): `accounts`, `transactions`, `categories`, `assignments`, `budget`, `payees`, `reconcile`, `recurring`, `rename-rules` (+ `rename-rules/apply`, `rename-rules/suggest` incl. optional AI suggestions), `duplicates`, `import` (+ `import/csv`), `export`, `snapshots`, `reset` (gated by `RESET_ENABLED=true`), `health`, `diagnostics/balance-integrity` + `diagnostics/budget-integrity`; shared error helper `errors.ts`.
- **Build/dev/test:** root `package.json` scripts delegate to `turbo run`; per-package `dev/build/typecheck/test`; Playwright e2e lives in `@ynab/web` (`tests/e2e/`, production `next start` on port 3100 against `budget.test.db`).

## 4. Data Flow
1. **UI action** (`@ynab/ui` view/modal) builds a typed payload via `logic/payload-builders.ts` (`action-payloads.ts` types).
2. **API call** to `apps/web/src/app/api/*` route → zod validation (`schemas.ts`) → delegates to `packages/server` query/use-case.
3. **Server write** goes through `server/transaction.ts` orchestration + domain `queries/*.ts` against Drizzle `schema.ts` (SQLite `budget.db`); `invariants.ts` + diagnostics endpoints enforce balance/budget integrity.
4. **Reads** return JSON consumed by `BudgetApp` state; derived budget math (available-to-budget, rollover, overspend) computed by `logic/budget-engine.ts`; formatting via `logic/format.ts`.
5. **Import/export:** `.y4backup`/CSV in via `server/import-ynab4.ts` / `import-csv.ts` (with `logic/csv-import.ts`, `duplicates.ts`, `rename-rules.ts`), out via `server/export-ynab4.ts`.
6. **Migrations/seeding:** `server/migrate*.ts` apply `migrations/*.sql`; `server/seed.ts` and `logic/seed-fixture.ts` bootstrap dev/test DBs (`budget.test.db`).
7. **Snapshots:** full `.db` file copies + `.json` sidecars in `snapshots/` next to the DB file (`server/snapshots.ts`, overridable via `SNAPSHOTS_DIR`).
8. **AI rename suggestions:** `server/queries/rename-suggest.ts` calls any OpenAI-compatible chat API via `server/llm.ts` (key read server-side only; enabled only when `LLM_API_KEY` + `LLM_MODEL` are set).

## 5. Key Design Decisions / Constraints
- Thin-web / fat-packages: `apps/web` has almost no business logic; rules live in `logic`, I/O in `server`, presentation in `ui`.
- Pure vs. effectful split: `logic` is side-effect free and unit-testable; all SQLite/Drizzle access confined to `server`.
- Single SQLite file DB with Drizzle + numbered SQL migrations; integrity checked by diagnostics endpoints, not just FKs.
- Node >= 20, TypeScript 5.9, Vitest per package, Playwright for e2e.
- Spending Sankey flow-through attribution (report-side only, `logic/sankey.ts` + `logic/transfers.ts` — the budget engine is untouched): off-budget accounts are intermediate pools, so any transfer touching one (a contribution out, a withdrawal back, or a move between two off-budget accounts — `isOffBudgetTransfer`) is excluded from both columns: movement, never terminal income or spending. The final purchase (wherever its account sits) is the one spending record; money is fungible, so each outflow is funded pro-rata by its traced inflow sources, which is exactly the report-wide proportional allocation the left hop already computes — if salary funded the investment account and the investment account later funded vacation spending, the Sankey shows salary → vacation, and chains of arbitrary depth collapse the same way. An off-budget account appears as income only for its external profit (dividends/interest/deposits recorded directly in it, grouped under the account's own name) — never pass-through principal; with no external inflows it contributes no source at all (clamped at zero) and the shortfall surfaces through the existing uniform-coverage shortfall (unfunded/Over-income), reducing every attributed source proportionally. Credit-card payoffs (internal transfers touching an on-budget credit account) stay excluded; categorized on-budget internal transfers still count as spending (legacy).
- Spending Sankey is three columns (report-side only, `computeSpendingGroupFlow` + `mergeGroupFlow` + `layoutGroupedIncomeSankey` in `logic/sankey.ts`, rendered by `ui/SpendingReport.tsx` with flows from `ui/ReportsView.tsx`): income sources (left) feed category groups (middle) by fungible proportional allocation, groups feed categories/merchants (right) by exact rollup attribution (merchants split across their transactions' groups; uncategorized spending routes through an "Uncategorized" pseudo-group). The right column owns the pixel scale so the long tail keeps its label pitch; surplus lands in a trailing Remaining target fed full-width from the incomes (identified by position, never by name); merged "Other" rows carry an explicit `bucket` flag because a bucket can hold a single row. Each ribbon carries one flat color through its whole length (no gradient) — the color of the node it flows into: left-hop ribbons the middle group's (Remaining green for the full-width surplus ribbons), right-hop ribbons the final category's or merchant's — so every flow reads as its destination and the income side never colors a ribbon. Each target belongs to its dominant (largest-link) parent group's color family (`sankeyTargetColors` in `ui/chartUtils.tsx`: darkest-first, so the largest sibling takes the darkest shade and smaller siblings lighten toward the parent color — more money reads darker), Sankey-only: the Bars rows keep their own full-brightness stable colors (`colorForName`), since the darkened family shades — tuned for translucent ribbon opacity — read too dark at the Bars' full opacity (task-31). Each middle→target cell draws as ONE ribbon carrying the full cell value — no per-income subdivision survives into the geometry (`GroupedRightLinkLayout` is one link per cell). Hovering an income, group, or ribbon spotlights its full flow path, while hovering a category/merchant bar spotlights only its dominant (largest-link) parent-group path — so a merchant split across groups traces its true home instead of every group's full funding fan; the path's ribbons brighten and render above the dimmed rest while everything outside dims, and the bars on the path brighten in the same bright color (every bar on all three columns shares its ribbons' exact fill at the ribbons' own rest/bright/dim brightness steps, so each line into a bar matches the bar in every state), with no CSS transition on the brightness steps — the z-reorder paints instantly, so a transition would show final z-order at pre-transition brightness and flash. Hover-leaves ride the same rAF throttle as hover-sets (`useRafThrottledSet` delivers null clears), so a direct A→B switch lands in one commit instead of flashing unchanged arms through rest (a synchronous clear beside throttled sets commits A→null→B across two frames). Bars wrap their funded flow on the absolute flow scale (`resolveFlowHeights`: a bar matches its ribbon stack, floored at the minimum label height), so there is no unfunded segment in the geometry — over-income gaps show in tooltips and the header, never as grey bar segments. Each income bar fills with a hard-edged top-to-bottom gradient of its outgoing ribbons' colors (`sankeyIncomeGradientStops`), one gradient per bar — never flat gray, never a hover overlay — with each bar segment matching its ribbon exactly — no borders, strokes, or halos on any bars in any state (an SVG stroke centers on the edge, so even a same-color hover stroke would paint 1px outside the bar and make it look bigger than its ribbon stack; hovering brightens via the spotlight instead). All bars paint with square corners, and the middle labels carry a fully opaque halo so no ribbon color bleeds through and tints them. Render-only rows — the merged Other buckets (grouped by the Under threshold) and the Remaining surplus plug — carry a hatch (`SankeyBucketHatchPattern`); Sankey tooltips carry only factual data (names, amounts, pure-data percentages — no explainer lines), and the column headers are plain labels with no hover. The right column sorts by current amount or by Budget order — parent group in Budget view group order, then each category's position in its parent group (`sortMergedGroupFlow` in `logic/sankey.ts`, Sankey view only — Bars stay by amount; merchants, which have no Budget position, stay value-descending within a group).
