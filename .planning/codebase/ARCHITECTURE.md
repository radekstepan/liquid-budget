# Architecture — YNAB4 Alternative SPA

## 1. Overview
- **What it is:** YNAB4-compatible envelope-budgeting personal finance app (YNAB4 data model: budget months, category groups/categories, payees, accounts, transactions with splits/transfers, monthly assignments, reconciliations, recurring templates).
- **Monorepo:** Yarn 4 workspaces (`apps/*`, `packages/*`), orchestrated by Turborepo (`turbo.json`: `dev`, `build`, `lint`, `typecheck`, `test`, `coverage`).
- **Runtime:** Next.js 16 (App Router) + React 19 SPA in `apps/web`; SQLite (better-sqlite3 via Drizzle ORM) persisted in `budget.db` (+ `budget.test.db`); Tailwind CSS 4.
- **Style:** Server owns persistence/migrations/queries; `logic` owns pure domain rules; `ui` owns all views; `web` is thin glue (routes + API handlers + shell).

## 3. Entry Points & Routing
- **Web entry:** `apps/web/src/app/layout.tsx` → `components/BudgetAppShell.tsx` → `@ynab/ui` `BudgetApp`. Client-side view routing via catch-all `app/(app)/[[...slug]]/page.tsx` — the slug selects only `budget` / `reports` / `transactions` (`AppView` in `logic/page-title.ts`, with optional month/account segments); other views (Payees, Snapshots, Themes, Settings, …) are in-app state, with `navVisibility.ts` controlling sidebar.
- **API surface** (`apps/web/src/app/api/*/route.ts`, validated by `schemas.ts` + zod): `accounts`, `transactions`, `categories`, `assignments`, `budget`, `payees`, `reconcile`, `recurring`, `rename-rules` (+ `rename-rules/apply`, `rename-rules/suggest` incl. optional AI suggestions), `duplicates`, `import` (+ `import/csv`), `export`, `snapshots`, `reset` (gated by `RESET_ENABLED=true`), `health`, `diagnostics/balance-integrity` + `diagnostics/budget-integrity`; shared error helper `errors.ts`.
- **Build/dev/test:** root `package.json` scripts delegate to `turbo run`; per-package `dev/build/typecheck/test`; Playwright e2e lives in `@ynab/web` (`tests/e2e/`, production `next start` on port 3100 against `budget.test.db`).

## 4. Data Flow
1. **UI action** (`@ynab/ui` view/modal) builds a typed payload via `logic/payload-builders.ts` (`action-payloads.ts` types).
2. **API call** to `apps/web/src/app/api/*` route → zod validation (`schemas.ts`) → delegates to `packages/server` query/use-case.
3. **Server write** goes through `server/transaction.ts` orchestration + domain `queries/*.ts` against Drizzle `schema.ts` (SQLite `budget.db`); `invariants.ts` + diagnostics endpoints enforce balance/budget integrity.
4. **Reads** return JSON consumed by `BudgetApp` state; derived budget math (available-to-budget, rollover, overspend) computed by `logic/budget-engine.ts`; formatting via `logic/format.ts`.
5. **Import/export:** `.y4backup`/CSV in via `server/import-ynab4.ts` / `import-csv.ts` (with `logic/csv-import.ts`, `duplicates.ts`, `rename-rules.ts`), out via `server/export-ynab4.ts`.
6. **Migrations/seeding:** `server/migrate*.ts` apply `migrations/*.sql`; `server/seed.ts` and `logic/seed-fixture.ts` bootstrap dev/test DBs (`budget.test.db`).
7. **Snapshots:** full `.db` file copies + `.json` sidecars in `snapshots/` next to the DB file (`server/snapshots.ts`, overridable via `SNAPSHOTS_DIR`).
8. **AI rename suggestions:** `server/queries/rename-suggest.ts` calls any OpenAI-compatible chat API via `server/llm.ts` (key read server-side only; enabled only when `LLM_API_KEY` + `LLM_MODEL` are set).

## 5. Key Design Decisions / Constraints
- Thin-web / fat-packages: `apps/web` has almost no business logic; rules live in `logic`, I/O in `server`, presentation in `ui`.
- Pure vs. effectful split: `logic` is side-effect free and unit-testable; all SQLite/Drizzle access confined to `server`.
- Single SQLite file DB with Drizzle + numbered SQL migrations; integrity checked by diagnostics endpoints, not just FKs.
- Node >= 20, TypeScript 5.9, Vitest per package, Playwright for e2e.
- Spending Sankey flow-through attribution (report-side only, `logic/sankey.ts` + `logic/transfers.ts` — the budget engine is untouched): off-budget accounts are intermediate pools, so any transfer touching one (a contribution out, a withdrawal back, or a move between two off-budget accounts — `isOffBudgetTransfer`) is excluded from both columns: movement, never terminal income or spending. The final purchase (wherever its account sits) is the one spending record; money is fungible, so each outflow is funded pro-rata by the inflow sources available when it occurs, which is exactly the chronological allocation the left hop computes (task-47: a fully-spent early income never funds late spending, while genuine savings still carry forward and arrears still resolve) — if salary funded the investment account and the investment account later funded vacation spending, the Sankey shows salary → vacation, and chains of arbitrary depth collapse the same way. An off-budget account appears as income only for its external profit (dividends/interest/deposits recorded directly in it, grouped under the account's own name) — never pass-through principal; with no external inflows it contributes no source at all (clamped at zero) and the shortfall surfaces through the existing uniform-coverage shortfall (unfunded/Over-income), reducing every attributed source proportionally. Money that never leaves those pools draws as first-class chart rows (task-49, replacing the task-48 Still-held strip): each still-held off-budget account (positive range net AND positive range-end balance — debt paydown into a negative-balance account is liability reduction, never holdings; fully-cycled or drawn-down accounts clamp to zero like profit) is a right-column target row named by the account, routed through the "Still held" pseudo-group in both dimensions and both views, funded chronologically by the same allocator — so income = spending + held + remaining everywhere and the Remaining plug shrinks to the on-budget leftover. "Starting Balance" rows are stock recognitions excluded from income, spending, and held alike; off-budget profit counts under the account name regardless of the `isIncome` flag (the import sets it false for every off-budget row and the engine ignores it there). Internal on-budget transfers of any kind (liquid-to-liquid moves, credit-card payoffs — `isInternalTransfer`) are excluded too, categorized or not: each leg names the OTHER account, so the two sides of a round-trip never share a payee to net under and the gross inflow would otherwise pile up as pass-through "spending" (task-35) — this matches the internal-transfer exclusion in `computeCashFlowRange`.
- Spending Sankey is three columns (report-side only, `computeSpendingGroupFlow` + `computeMonthlySankeySeries` + `computeSankeyViewModel` + `layoutGroupedIncomeSankey` in `logic/sankey.ts`, rendered verbatim by `ui/SpendingReport.tsx` with flows and series from `ui/ReportsView.tsx`): income sources (left) fund each middle→target cell chronologically (task-47: each month's income joins a per-source pool funding that month's and later cell demands, so hovering a merchant spotlights only income that could actually have funded it — a 2015 income fully spent in 2015 never lights for 2020 spending), groups feed categories/merchants (right) by exact rollup attribution (merchants split across their transactions' groups; uncategorized spending routes through an "Uncategorized" pseudo-group, still-held accounts through a "Still held" one). Math-first (task-44): the layout owns every drawable — nodes, ribbon and sub-ribbon paths, bar gradient stops, fills, label anchors — as reproducible JSON-serializable objects, and the view holds no geometry, subdivision, path, color, or label math; glitches are fixed in the layout, never in the render. The right column owns the pixel scale so the long tail keeps its label pitch; surplus lands in a trailing Remaining target fed full-width from the incomes through a dedicated lane below the middle column (identified by position, never by name; the lane is transit-only — bars keep their stacked spots); each plug ribbon drops from its source band into the lane, bridges under the group bars, then traverses to the plug bar, crossing no bar and no middle→target ribbon (the traverse shares the right-hop x-range and curve family, so the crossing-freedom is exact — only the drop still crosses income→group ribbons in the left half, topologically unavoidable like the group-group crossings); merged "Other" rows carry an explicit `bucket` flag because a bucket can hold a single row. Each ribbon carries one flat color through its whole length (no gradient) — the color of its FINAL (right-column) destination: right-hop ribbons the final category's or merchant's (one ribbon per group→target cell), and in Categories grouping each left-hop income→group band subdivides into one sub-ribbon per downstream cell (layout `leftCells`) in the same category colors, landing in contiguous per-color blocks so each color crosses the middle at exactly its cell's thickness (task-43's band-local nesting conserved per color only with a single income; the same-income braiding this costs is topologically minimal) — Remaining green for the full-width surplus ribbons, and in Merchants grouping each left-hop band subdivides the same way into per-merchant sub-ribbons (a merchant spanning groups repeats its color down the bar, once per band it funds) — so every flow reads as its destination and the income side never colors a ribbon. Each target keeps its own stable color (`sankeyTargetColor`, canonical in `logic/sankey.ts` and re-exported by `ui/chartUtils.tsx` since task-44 — the category determines the color and it flows backwards along every ribbon arriving at it, no matter which middle group each ribbon comes from; the parent group never tints it; buckets resolve by flag, never by name, so a literal "Other" row keeps its hash color), so the Sankey bars and the Bars rows share the same palette row for row (the earlier dominant-group family shades were removed in task-35). Each middle→target cell draws as ONE ribbon carrying the full cell value — no per-income subdivision survives into the right-hop geometry (`GroupedRightLinkLayout` is one link per cell). Hovering an income, group, ribbon, or category/merchant bar spotlights its full flow path — a target lights EVERY cell arriving at it (including ribbons from non-dominant parent groups), every parent group feeding those cells, and the income slices funding those cells — with per-sub-ribbon granularity on subdivided bands (a sub lights only when both its band and its cell sit on the path), so a target hover lights only its own slices out of a shared band (task-45) and each income bar lights only when one of its slices into the target lights (task-47: funding the group for other rows is not enough) — so a merchant split across groups traces its whole story instead of one dominant home (task-35); each row on every column is one hover target (handlers on the wrapping `<g>`; the right column adds a transparent hit band bridging the bar→label gap (task-37) and the left column mirrors it from the SVG's left edge to the bar's right edge, while the middle column deliberately has no band — its labels sit in the ribbon zone, so a band would swallow ribbon hovers (task-42)), so moving between a row's bar, title, and amount never flickers the spotlight; the path's ribbons and bars brighten in place while everything outside dims (every bar shares the ribbons' own rest/bright/dim brightness steps; income segments, middle segments, and target bars also share their ribbons' exact fill — the group hue survives only on the tooltip dot and the no-income fallback), and the brightness steps cross-fade over 120ms (zero under prefers-reduced-motion) — flash-safe because the DOM order never changes with hover (no z-reorder, so no final z-order can show at pre-transition brightness — the task-29 hazard — and brightness alone carries the spotlight). Hover-leaves ride the same rAF throttle as hover-sets (`useRafThrottledSet` delivers null clears), so a direct A→B switch lands in one commit instead of flashing unchanged arms through rest (a synchronous clear beside throttled sets commits A→null→B across two frames). Bars wrap their funded bands exactly (no minimums, no stealing — the only floor is the per-band visibility floor), so there is no unfunded segment in the geometry — over-income gaps show in tooltips and the header, never as grey bar segments. Every row reserves label pitch and labels anchor at the layout's `labelY` verbatim (task-44: view-side centering used to park hairline labels on their slivers, hiding thin ribbons under the label halo); the SVG canvas fits the layout's `contentHeight` (task-44: the old row-count heuristic clipped fat bars). Each income and middle bar paints the layout's own hard-edged gradient stops (`sourceFills`/`middleFills`) verbatim, one gradient per bar — never flat gray, never a hover overlay — with no dimension split (task-38's income-side split was removed in task-46): in both groupings each income→group band subdivides by the group's downstream cells — categories in Categories grouping (exact because each category has one group), merchants in Merchants grouping — so target colors drive the bar's segments — while middle bars always segment by their outgoing cells' target colors in both groupings (task-41; one ribbon per cell holds in both, so no dimension split is needed, and a bar with no outgoing bands falls back to its solid group color) — with each bar segment matching its ribbon exactly — no borders, strokes, or halos on any bars in any state (an SVG stroke centers on the edge, so even a same-color hover stroke would paint 1px outside the bar and make it look bigger than its ribbon stack; hovering brightens via the spotlight instead). All bars paint with square corners, and the middle labels carry a fully opaque halo so no ribbon color bleeds through and tints them. Computed/derived money — the merged Other buckets (grouped by the Under threshold), the Remaining surplus plug, and still-held balances (task-50: the hatch means derived, not terminal purchases) — carries a hatch (`SankeyBucketHatchPattern`): whole-held elements only — held target bars, the whole-held Still-held group bar, right-hop ribbons into held targets, and left-hop sub-ribbons funding held cells each overlay the same geometry with the shared pattern (mixed bars, segments, and buckets stay solid); task-51 extends the ribbon hatch to the Other buckets and the plug (right-hop ribbons into bucket targets, full-width plug-lane ribbons, and left-hop sub-ribbons funding bucket/plug cells) — destination-driven, so ribbons out of a middle bucket into a real target stay solid; the Bars view reuses that exact pattern def for its merged Other bucket bars and held rows (one shared def + per-bar overlay rect, since Bars rows are HTML divs — never a lookalike — and Bars render no Remaining plug); Sankey tooltips carry only factual data (names, amounts, pure-data percentages — no explainer lines), and the column headers are plain labels with no hover. The right column sorts by current amount or by Budget order — parent group in Budget view group order, then each category's position in its parent group (`sortMergedGroupFlow` in `logic/sankey.ts`, Sankey view only — Bars stay by amount; merchants, which have no Budget position, stay value-descending within a group).
